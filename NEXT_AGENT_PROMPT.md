**Task Description:**
The user is experiencing an issue where the public tunnel QR code generated by the Arbor Mobile Companion fails to load on their mobile device.

**Symptoms:**
1. The user launches the mobile companion using a tunnel provider (like Pinggy).
2. A QR code and a text link are generated.
3. The user scans the QR code with their mobile phone. It scans successfully and opens the browser, but the browser displays an error stating "there might be a typo in the url" (or "server cannot be found" / `ERR_NAME_NOT_RESOLVED`).
4. If the user copies the exact text link displayed in the laptop UI and opens it in their laptop browser (on the same Wi-Fi), it works perfectly.

**What was already investigated and ruled out by previous agents:**
1. **QR Code Formatting/Density:** A previous agent updated `qrcode.QRCode(box_size=4, border=4)` to ensure standard compliance.
2. **Hidden Characters or Typos in the QR Code:** The second agent extracted the raw data directly from the user's QR code screenshot using OpenCV. The decoded payload was a flawless URL (e.g., `https://3bc27e88de7f1067...serveousercontent.com?token=...`) with exactly 101 ASCII characters and **no hidden ANSI escape codes or invisible characters**. The QR code itself is generating perfectly.
3. **Provider Fallback Logic:** The second agent noticed that the user selected "Pinggy" but the screenshot showed a "Serveo" URL. This happened because `PinggyTunnel` was just an alias for `ResilientSSHTunnel`, which hardcoded Serveo as the first priority. The agent refactored `PinggyTunnel` to use a `preferred_provider` parameter to force it to actually try Pinggy first. **However, the user reports the issue still persists.**

**Investigation Leads for the Next Agent:**
1. **Silent Fallback:** Check if the SSH command to connect to Pinggy (`a.pinggy.io`) is failing silently on the user's machine (e.g., due to port 443 being blocked for SSH by their ISP/firewall), causing `ResilientSSHTunnel` to fall back to Serveo anyway, putting the user back at square one where Serveo is blocked by their mobile DNS.
2. **Mobile DNS / Carrier Blocking:** If the user is now successfully getting a Pinggy URL (`*.pinggy.link` or `*.pinggy.net`) but their phone still says "typo in the url", this strongly indicates their mobile device's DNS is blocking Pinggy as well. Look into whether we can use Cloudflare tunnels (`trycloudflare.com`) as the ultimate unblockable default, or if there is an IPv4 vs IPv6 resolution discrepancy on the mobile device.
3. **QR Code URL Parsing on Mobile:** Investigate if there is something specific about the URL structure (like the query parameter `?token=...`) that is causing mobile browsers to truncate the URL before doing the DNS lookup.
